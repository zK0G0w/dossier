# 写作类任务

产出给人看的成品文档：方案、周报、邮件、评审意见、技术文档。

## 开工前

问清楚**给谁看**和**要解决什么** —— 周报和技术方案的写法完全不同。受众是老板 / 同事 / 外部？要说服还是要知会？

## 执行

### 先骨架后血肉

不要一上来就写正文。先列骨架（一级标题 + 每段一句话的核心论点），给用户看一眼：

```markdown
# 方案：XXX

## 背景（现状 + 问题）
一句话：现在怎样，哪里不行。

## 方案（做什么）
一句话：要做什么，边界在哪。

## 技术设计（怎么做）
- 子系统 A：核心改动点
- 子系统 B：核心改动点

## 风险与对策
- 风险 1 → 对策
- 风险 2 → 对策

## 排期
关键里程碑 3-4 个
```

骨架过了再展开，未通过不要展开正文。

### 存多版本

初稿叫 `草稿-v1.md`，改完存 `草稿-v2.md`，最终版叫 `终稿.md`。用户想看「改了哪」时能直接 diff。草稿不用删 —— 复盘时草稿比终稿更有价值。

### 语言风格跟场景

- **周报 / 邮件**：短句、主动语态、结论前置，如「完成了 X，发现了 Y，下周做 Z」，避免「本周主要工作围绕...」式的开头。时间节点写死（「Q3 上线」「2026-09-15 前」），不用「目前」「暂时」「后续」等模糊词。
- **技术方案**：准确 > 优雅。用术语，列参数，画图（ASCII art / mermaid 都行），给出边界条件。不确定的事标「待验证」，不要写成定论。
- **评审意见**：逐条，标序号，分「阻塞项」和「建议项」。不要把风格偏好包装成技术问题。

### 用清单自查

写完后过一遍：
- [ ] 标题能让人一眼看出这是干什么的？
- [ ] 第一段就给出了核心结论 / 要做的事？
- [ ] 每个「因此」「所以」前面的推理链条都说清楚了？
- [ ] 没有「进一步」「相关」「优化」这种模糊词？
- [ ] 如果有决策分支（为什么选 A 不选 B），理由写出来了？

过不了就改，过了再交付。
